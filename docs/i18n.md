# Internationalization

Stockly ships in **Thai (`th`)** and **English (`en`)**. Adding a third language is a member in one
array, a directory of JSON, and nothing else.

The rule the whole layer exists to preserve:

> **A locale decides what a number is called. It can never decide what the number is.**

`domain/locale-boundary.test.ts` proves it rather than asserting it: it runs every locale operation
the application performs and requires holdings, cost basis, realized and unrealized P&L, and cash to
be byte-identical afterwards.

---

## The decisions, and why

| Decision | Choice | Why |
|---|---|---|
| Library | `next-intl`, no locale routing | Locale comes from a cookie, not a path. Adding `[locale]` segments would have moved every route and forced the CSP nonce flow, share/snapshot tokens, the service-worker scope, `robots.ts` and `sitemap.ts` to be reconciled with a prefix — for a preference, not an address. |
| Default | `th` | A product decision, not `Accept-Language`. It is also what an anonymous visitor to a public share page gets, and a share link's language should be something its owner can reason about. |
| Thai calendar | **Gregorian**, pinned | `th-TH` resolves to the Buddhist era in ICU. The same trade date would read 2569 in Thai and 2026 in English — one transaction, two years — across screenshots, exports, audit trails and support conversations. `LOCALE_META.th.intlTag` is `th-TH-u-ca-gregory`: Thai month names, Christian era. |
| Currency | **Never derived from language** | `Language: ไทย, Currency: USD` and `Language: English, Currency: THB` both work. Currency is a property of a portfolio. |
| Timezone | **Never derived from language** | A Thai reader in New York sees Thai month names and New York clock time. Calendar dates are formatted in UTC; market times come from `domain/calendar.ts` in the market's own zone. |

## Where things live

```
domain/locale.ts            the registry: SUPPORTED_LOCALES, Locale, DEFAULT_LOCALE, LOCALE_META,
                            isLocale/toLocale/matchLocale, intlTag. Imports nothing at all.
lib/i18n/namespaces.ts      the list of namespaces — the contract the completeness test checks
lib/i18n/request.ts         next-intl's getRequestConfig; wired by next.config.ts
lib/i18n/resolve.ts         resolveLocale() for the app, resolvePublicLocale() for shared pages
lib/i18n/server.ts          appLocale() — the short code, in a Server Component
lib/i18n/locale.ts          useAppLocale() — the short code, in a Client Component
lib/i18n/errors.ts          useErrorMessage() — an API error code becomes a sentence
lib/api-codes.ts            the error vocabulary, with no server imports so the browser can read it
locales/{th,en}/*.json      one file per namespace
locales/{th,en}/index.ts    the barrel; static imports so only the active locale is bundled
features/i18n/              the switcher and the cookie writer
```

## Namespaces

**A namespace is a feature slice**, plus six cross-cutting ones. A string used by
`features/transactions` goes in `transactions.json`; a button label used by nine features goes in
`common.json`. There is no third option to weigh, which is the point.

`common`, `navigation`, `enums`, `errors`, `validation`, `metadata`, `settings` — plus one per
directory in `features/`.

## Using it

```tsx
// Client Component
const t = useTranslations("transactions")
<h1>{t("title")}</h1>

// Server Component
const t = await getTranslations("transactions")

// Interpolation and plurals — never a ternary
t("results", { count })          // "{count, plural, =0 {…} one {# result} other {# results}}"

// An enum value, never rendered raw
const tEnum = useTranslations("enums")
tEnum(`cashFlow.${row.kind}`)

// An API failure
const describeError = useErrorMessage()
onError: (error) => toast.error(describeError(error))
```

### Dates

Every date formatter in `lib/format.ts` takes a `Locale`, **required**, so the compiler finds every
call site rather than a reviewer.

```tsx
formatDate(transaction.trade_date, locale)     // "03 ก.ย. 2026" / "Sep 03, 2026"
formatLongDate(published, locale)              // "3 กันยายน 2026" / "September 3, 2026"
formatTime(quote.asOf, locale)                 // viewer's timezone, translated month
```

### Money, quantities, percentages — no locale

Measured, not assumed. Across `en-US` and `th-TH-u-ca-gregory`, `Intl` produces **byte-identical**
output for every money, quantity, percentage and compact figure Stockly renders — Thai uses Latin
digits, comma grouping and a decimal point:

```
en-US               ฿1,234,567.89  $1,234,567.89  1,234,567.12345  4.4T  38M
th-TH-u-ca-gregory  ฿1,234,567.89  $1,234,567.89  1,234,567.12345  4.4T  38M
```

So `formatCurrency` takes no locale. That is not an omission — it is the mechanism by which
"Thai and English produce exactly the same financial result" is *true* rather than merely tested.
`domain/locale-boundary.test.ts` pins the equality against `Intl` directly, so a future ICU release
cannot break it quietly.

## How a locale is resolved

**In the app**, `lib/i18n/resolve.ts`:

```
cookie (stockly_locale)          the switcher's most recent, most explicit statement
  ↓ absent
user_preferences.locale          consulted once, on a device they have not used before
  ↓ absent / anonymous
DEFAULT_LOCALE ("th")
```

The cookie sits above the database deliberately, so a page render never waits on a query to answer a
question the cookie already answered. The visible consequence, documented rather than hidden:
**changing the language on one device does not retune a device that is already open.** The switcher
writes both, so the next device to sign in picks it up.

**On a public page** (`/p/:slug`, `/share/:token`, `/snapshot/:token`), `resolvePublicLocale`:

```
?lang=th|en   →   this device's cookie   →   DEFAULT_LOCALE
```

Different function, different first source, because the reader is a different person. A visitor has
no preference row, and the *owner's* cookie must never decide the language of a page a stranger is
reading. `PublicPortfolioView` therefore takes `locale` as a **prop** and cannot resolve it itself.

### Security

The cookie is not `HttpOnly` — the switcher writes it in the browser so an anonymous visitor can
change language without an account — and it is `SameSite=Lax`, `Secure` over HTTPS. Every read goes
through `toLocale`, a closed-enum check, so the worst a hand-edited cookie or a crafted `?lang=`
achieves is the default language. Neither value is ever echoed into the page. No translation is
rendered through `dangerouslySetInnerHTML`.

## What is *not* translated

- **Anything a user wrote.** Portfolio names, notes, journal entries, theses, tags, custom labels.
  These are stored as typed and rendered as typed.
- **Provider content.** News headlines, summaries, company descriptions, fundamental figures. Stockly
  has no translation capability it can vouch for, and a headline attributed to a real publication in
  words it never wrote is a false statement about a named organisation. The chrome *around* it —
  "Source", "Published", "Category" — is translated; the article is not.
- **Machine-readable output.** API request and response schemas, CSV export headers, database
  values, enum codes on the wire. A locale must never change what an integration parses.
- **`app/global-error.tsx`**, which is deliberately bilingual: it replaces the whole document, so it
  has no provider. Showing both languages is three lines and always correct; guessing one is
  sometimes wrong at the worst possible moment.

## Testing

`lib/i18n/completeness.test.ts` runs per namespace and fails on:

- a namespace file that exists in one locale and not the other
- a namespace on disk that no barrel imports (so nothing in it is reachable)
- a key present in one language and missing in the other — **checked both directions**
- an empty translation, which renders as nothing and looks like a layout bug
- a placeholder that survives one language and is dropped in the other, so `{count}` appears
  verbatim on screen in exactly one locale
- a Thai file that is a copy of the English one

`domain/locale-boundary.test.ts` proves the financial invariant, the Gregorian era, the closed-enum
validation, and that `domain/locale.ts` still imports nothing.

## Missing keys

Development throws into the console. Production logs `i18n.message` with the code and renders the
key path — ugly, obviously wrong, and greppable. Neither is the guarantee; the completeness test is.
The fallback chain is *requested locale → the key path*, never English-behind-Thai: a half-English
sentence reads as a bug in the translation rather than as a missing string, and is harder to find.

## Adding a language

1. Add it to `SUPPORTED_LOCALES` and give it a `LOCALE_META` row — including the `intlTag`, where
   any calendar or numbering decision for that language is made **once**.
2. `cp -r locales/en locales/<code>` and translate. Regenerate the barrel from `NAMESPACES`.
3. Add it to the `locale` check constraint on `user_preferences`.
4. Run the suite. The completeness test will name every key you have not done.

Nothing else changes. No route, no domain function, no component.

## Adding a string

Never inline it. Put it in the namespace of the feature that owns it, in **both** languages, and use
`t()`. The completeness test is what stops the second language being "later".
